### Q1: Why did you choose this seminar topic?
**Answer**:

### Q2: How does your project relate to the two selected ACL 2026 research papers?
**Answer**:  
- **Paper 1 (Peng et al., ACL 2026: FCV-Attack)** introduced the concept of **Functionally Correct yet Vulnerable (FCV)** patches—patches that pass unit test cases but leave severe CWE security flaws. My project explicitly tests AI patches for FCV threats.
- **Paper 2 (Chen et al., ACL 2026: SecureVibeBench)** established a multi-oracle benchmark that evaluates agents across four categories: `C-SEC` (Correct & Secure), `C-SUS` (Correct & Suspicious), `C-VUL` (Correct & Vulnerable), and `IC` (Functionally Incorrect). My project adopts this exact 4-way evaluation matrix.
- **Clarification for Viva**: My project is a **supplementary experimental prototype** inspired by these papers. It focuses on an ML-assisted static auditing detector and does not claim to execute full repository-level fuzzer suites or Docker sandbox environments.

### Q3: What is the fundamental difference between Functional Correctness and Security Safety?
**Answer**:  
- **Functional Correctness** verifies that software satisfies specified functional requirements for intended user inputs (e.g., computing a curve value or creating a directory). It is tested using standard unit tests.
- **Security Safety** ensures that software resists unexpected, malicious, or boundary inputs without exposing security weaknesses (e.g., buffer overflows, memory leaks, or command injection).
- Passing unit tests does **not** prove security safety. An AI agent might write a patch that clamps an lower bound to pass unit tests, but omit the upper bound clamp, leaving a heap buffer overflow vulnerability (`C-VUL` / FCV patch).

---

### Q4: What is a CWE, a SAST tool, and a PoV program?
**Answer**:  
- **CWE (Common Weakness Enumeration)**: A community-developed formal dictionary of security weakness types (e.g., CWE-120 for Buffer Copy without Size Check, CWE-416 for Use-After-Free, CWE-78 for Command Injection).
- **SAST (Static Application Security Testing)**: Static code analysis tools (like Semgrep or Cppcheck) that scan source code for known security vulnerability patterns using AST or regex rules without executing the code.
- **PoV (Proof-of-Vulnerability)**: An executable script or input test case designed to trigger a specific security exploit in a program (used as a dynamic security oracle in benchmarks like SecureVibeBench).

### Q5: Explain your dataset design and how you prevented Data Leakage.
**Answer**:  
- **Dataset Composition**: 640 C/C++ code functions split evenly (320 Secure, 320 Vulnerable) covering CWE-120/122, CWE-416, CWE-415, CWE-476, CWE-78, and CWE-190.
- **Preventing Data Leakage**: Data leakage occurs when test data characteristics leak into the training process. I prevented this by:
  1. Using **Stratified 80/20 Train-Test Splitting** (`seed=42`) *before* feature extraction.
  2. Fitting the `TfidfVectorizer` and domain feature extractor **only on the training split** (`X_train`), and applying `transform()` to `X_test`.
  3. Removing string literals and comments via normalization (`"STR_LITERAL"`, `NUM_HEX`) so models learn generic structural patterns rather than memorizing variable names.

### Q6: What feature extraction techniques did you use?
**Answer**:  
I implemented a **hybrid feature extraction pipeline**:
1. **Lexical Token N-Grams**: TF-IDF vectorization of C/C++ token n-grams (ranges 1 to 3) capturing word sequences and syntax patterns.
2. **C/C++ Security Domain Features (15 Features)**:
   - Counts of dangerous string APIs (`strcpy`, `gets`, `sprintf`).
   - Counts of command execution APIs (`system`, `popen`).
   - Counts of memory allocation and free APIs (`malloc`, `free`).
   - Pointer dereference frequency (`->`, `*`).
   - Binary flags for presence of bounds checks (`sizeof`, `strlen`, `<`) and NULL pointer checks (`NULL`, `nullptr`).
   - Ratio of resetting pointers after `free()` (`ptr = NULL`).
   - Integer overflow indicators on allocation sizes.

### Q7: Why did you choose Random Forest over Deep Learning for this seminar project?
**Answer**:  
1. **Performance & Lightweight Execution**: Random Forest trains in under 5 seconds on standard CPU hardware without requiring expensive GPUs.
2. **Interpretability**: Provides explicit Gini impurity feature importances, allowing us to explain *why* a snippet was flagged (e.g., presence of `strcpy` combined with missing `sizeof` bounds checks).
3. **High Recall & Robustness**: Handles non-linear feature interactions and high-dimensional sparse TF-IDF matrices effectively without overfitting.

### Q8: Why are Recall and False Negative Rate (FNR) more critical than Precision in Security Evaluation?
**Answer**:  
- In security auditing, a **False Positive (FP)** means a safe patch is flagged for review (causing minor inconvenience).
- A **False Negative (FN)** means a vulnerable patch goes undetected and gets merged into production, allowing attackers to exploit the software.
- Therefore, we optimize for **High Recall (Sensitivity)** and **Low False Negative Rate (FNR)** to minimize undetected security risks.

---

### Q9: What is the difference between an ML prediction and a Confirmed Vulnerability?
**Answer**:  
An ML model prediction represents a **probabilistic classification score** (e.g., 85% risk of CWE-120) based on learned code patterns. It indicates a *suspected* vulnerability. A **confirmed vulnerability** requires dynamic verification (e.g., executing a PoV exploit in a sandbox or manual security analysis proving reachability and impact).
