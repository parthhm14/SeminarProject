## 1. Project Title
**ML-Assisted Security Evaluation of AI-Generated C/C++ Code**

---

## 2. Motivation
Large Language Models (LLMs) and autonomous software engineering code agents (such as SWE-agent, OpenHands, Aider, and Claude Code) are rapidly transforming modern software development. While these agents demonstrate impressive capabilities in resolving GitHub issues and writing code patches, software security has emerged as a critical concern.

Traditional software evaluation relies on **functional test suites** (unit and integration tests). However, recent research presented at **ACL 2026** reveals that functional correctness does not guarantee security safety. Code agents frequently generate patches that pass all functional test cases while simultaneously introducing high-severity memory-safety vulnerabilities (e.g., buffer overflows, use-after-free, command injections). Developing rapid, automated, machine-learning-assisted security evaluation mechanisms is therefore essential to prevent insecure AI-generated code from entering production codebases.

---

## 3. Problem Statement
Given C/C++ source code patches generated or modified by AI coding agents, how effectively can a lightweight machine-learning detector—augmented with lexical code token n-grams and domain-specific C/C++ security features—identify latent security vulnerabilities and distinguish between functionally correct secure patches (`C-SEC`), suspicious patches (`C-SUS`), vulnerable patches (`C-VUL`), and incorrect outputs (`IC`)?

---

## 4. Research Objectives
1. **Dataset Construction**: Assemble a reproducible, leak-free C/C++ dataset covering major Common Weakness Enumeration (CWE) memory safety categories (CWE-120/122, CWE-416, CWE-415, CWE-476, CWE-78, CWE-190).
2. **Feature Engineering**: Design a hybrid feature extraction pipeline combining TF-IDF lexical token n-grams with 15 domain-specific C/C++ security features (dangerous string APIs, pointer arithmetic, missing bounds checks, allocation-free balance).
3. **Model Development**: Implement and compare a baseline linear model (Logistic Regression) against an advanced ensemble model (Random Forest Classifier).
4. **AI Patch Benchmark Evaluation**: Evaluate the trained detector and a SAST rule scanner on a controlled suite of 24 AI-generated C/C++ patch cases modeled after real-world scenarios in **SecureVibeBench**.
5. **Empirical Analysis**: Evaluate metrics (Accuracy, Precision, Recall, F1, FPR, FNR, ROC-AUC), perform error analysis, and discuss why functional testing is insufficient for software security.

## 5. Connection to Selected Research Papers

### Paper 1: *"When 'Correct' Is Not Safe: Can We Trust Functionally Correct Patches Generated by Code Agents?"* (Peng et al., ACL 2026)
- **Conceptual Grounding**: Paper 1 introduces the threat of **Functionally Correct yet Vulnerable (FCV)** patches and the **FCV-Attack** vector, showing that agents can be manipulated or naturally output code that passes test suites but remains exploitable.
- **Project Incorporation**: Our project explicitly measures the FCV rate (`C-VUL` category) within AI-generated patch samples, validating Paper 1's thesis that test-pass rates misrepresent security safety.

- **Project Incorporation**: Our evaluation framework adopts Paper 2's four-way classification matrix and evaluates AI patches inspired by SecureVibeBench repository tasks (HarfBuzz, Leptonica, rawSpeed, Wireshark, OpenSSL, curl).

## 7. Dataset & Preprocessing

- **Dataset Size**: 640 total C/C++ code functions/snippets.
- **Class Balance**: 50% Secure (320 samples), 50% Vulnerable (320 samples).
- **Data Splitting**: Stratified 80% Training (512 samples) and 20% Testing (128 samples) with fixed random seed (`seed=42`) to prevent data leakage.
- **Preprocessing Steps**:
  1. Comment Removal: Single-line (`//`) and multi-line (`/* ... */`) comments stripped.
  2. Literal Abstraction: Double-quoted strings replaced with `"STR_LITERAL"`; hex/dec constants replaced with `NUM_HEX`/`NUM_DEC`.
  3. Tokenization: Regular expression lexing for C/C++ keywords, identifiers, and operators (`->`, `==`, `&&`, etc.).

## 8. Machine Learning Models

1. **Baseline Model (Logistic Regression)**:
   - Linear classifier using TF-IDF token features.
   - Hyperparameters: `C=1.0`, `max_iter=1000`, `class_weight='balanced'`, `random_state=42`.
2. **Advanced Model (Random Forest Classifier)**:
   - Non-linear ensemble model combining TF-IDF tokens with C/C++ domain security features.
   - Hyperparameters: `n_estimators=150`, `max_depth=15`, `class_weight='balanced'`, `n_jobs=-1`, `random_state=42`.

## 9. Experimental Setup & Metrics

Experiments were executed on a Windows 11 host (Intel CPU, 16GB RAM) in a Python 3.12 environment using `scikit-learn`, `pandas`, `numpy`, `matplotlib`, and `seaborn`.

**Evaluation Metrics**:
- **Accuracy**: $\frac{TP + TN}{TP + TN + FP + FN}$
- **Precision**: $\frac{TP}{TP + FP}$
- **Recall (Sensitivity)**: $\frac{TP}{TP + FN}$ (Crucial for security to minimize undiscovered vulnerabilities)
- **F1-Score**: $2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$
- **False Positive Rate (FPR)**: $\frac{FP}{FP + TN}$
- **False Negative Rate (FNR)**: $\frac{FN}{FN + TP}$
- **ROC-AUC**: Area under the Receiver Operating Characteristic curve.

## 11. Error Analysis & Security Interpretation

1. **Why High Recall is Critical**: In software security auditing, **False Negatives (FNR)** are far more dangerous than False Positives (FPR). A false negative means a vulnerable AI patch is approved and merged into production software, creating an attack vector for exploitation.
2. **The FCV Paradox**: **58.3%** of evaluated AI patches were categorized as `C-VUL`. Agents frequently fix the functional bug described in the prompt (e.g. clamping a lower bound on an integer interpolation) but fail to add defensive upper bound checks or sanitize command inputs.
3. **SAST False Alarm Trade-off**: SAST scanners provide static pattern coverage but incur false positives (e.g. flagging safe `system()` calls in test utilities as suspicious `C-SUS`). ML classifiers trained on domain features provide complementary probability scores to help filter SAST noise.

---

## 12. Limitations

1. **Dataset Scope**: The current dataset focuses on core C/C++ memory safety CWEs. Higher-level web application vulnerabilities (e.g. XSS, SQLi) in Python/JS are outside the scope.
2. **Static vs. Dynamic Analysis**: Static ML predictions cannot fully replace dynamic Proof-of-Vulnerability (PoV) execution or symbolic execution for complex multi-threaded concurrency bugs.
3. **Offline Prototype**: The AI patch suite uses a controlled set of 24 representative patch cases rather than running real-time multi-file SWE-agent scaffolding across 100+ Docker repositories.
